开了代理进终端, 即使 ping 通了 GitHub，为何依然是直连？

Ping 通了 GitHub，不代表你走了代理

平时在终端里拉取 GitHub 仓库或者下载 release 资产时，时不时就会遇到速度慢如蜗牛甚至直接连接超时的情况。今天在 Windows 的 PowerShell 终端里给它配上了本地代理，本以为只是个几分钟搞定的顺手小事，没想到在这个过程中接二连三地踩进了自己的“认知盲区”。

1. 起因：一个理所当然的“顺手测试”

在终端里开启代理配置之后，我下意识地在命令行敲了一句：

ping github.com

终端很快就返回了结果：

来自 20.205.243.166 的回复: 字节=32 时间=105ms TTL=111
来自 20.205.243.166 的回复: 字节=32 时间=106ms TTL=111
...
数据包: 已发送 = 4，已接收 = 4，丢失 = 0 (0% 丢失)

看到 105ms 的延迟而且 0 丢包，我理所当然地认为之前开启的代理软件生效了。

不过我又随手测了一句：

ping google.com

结果屏幕直接卡住，十几秒后, 等待我的结果是，蹦出来一行行的 请求超时，100% 丢包。

这时候我有点疑惑：如果代理真的开了，为什么 Google 通不了？而如果代理没开，为什么平时连接费劲的 GitHub 却能 ping 通？

2. 探究：原来我搞混了协议层级

带着这个困惑去梳理网络底层原理，才发现自己犯了一个常识错误：ping 根本不会走常规的本地代理。

这里先附上张网络分层与代理工作机制的对照图：

平时我在终端配置的环境变量：

$env:HTTP_PROXY="http://127.0.0.1:7890"; $env:HTTPS_PROXY="http://127.0.0.1:7890"

这类代理服务（比如 Clash、v2rayN 等常见的本地 7890 端口）工作在传输层 / 应用层（TCP/UDP）。只有那些支持 HTTP 代理协议、并主动去读取环境变量的软件（例如 curl、git、浏览器、各种包管理器），才会把数据包打包发给 127.0.0.1:7890 进行中转。

而 ping 命令使用的是网络层的 ICMP 协议。
它在操作系统底层工作，既不走 TCP，也不走 HTTP，在发包时会彻底无视我设置的任何代理环境变量，数据包依然是从物理网卡直连发出的。

那么，为什么平时打不开 GitHub，直连 ping 却能通？

我依然保留的这个疑问：平时我不开代理连 GitHub 都卡死，现在 ping 通了，难道不是代理把它加速了吗？

其实并不是：

  1. 平时 GitHub 打不开，卡在“应用层”

GitHub 的服务器归微软所有，国内访问它困难，主要原因是 DNS 污染、HTTPS 握手时的 SNI 域名阻断，或者是 TCP 传输被间歇性干扰限速。也就是说，拦截和干扰主要发生在应用层与传输层。

  1. 底层物理网络其实并没有被完全掐断

ping 发出的是最基础的 ICMP 探测包，里面没有域名，也没有 HTTP 数据。国内运营商骨干网可能并没有在 IP 层面完全拉黑 GitHub 的亚太机房 IP（比如上面日志里的 20.205.243.166 微软新加坡节点）。

  1. AI推测的可能情况

那个 ping 通了的响应，本身就是本地宽带直接顺着海底光缆打到微软新加坡节点返回的物理延迟。就算把代理软件彻底关掉，在终端里敲 ping github.com，只要当时本地链路没发生严重丢包，它大概率依然是直连通的。

因此，ping google.com 超时是因为它的 IP 被直接拦截，而 ping github.com 通了只是普通的直连物理网络没被阻断。拿 ping 去判断代理有没有生效，从一开始就找错了参照物。

(注：除非代理软件开启了基于虚拟网卡的 TUN 全局模式接管整张网卡，否则常规代理下 ping 永远是本地直连)

3. 正确姿势：如何验证终端代理

搞清楚不能用 ping 之后，我们可以用 curl -I 验证应用层连通性。

既然代理工作在应用层，就应该用应用层的工具来测试。curl 原生支持读取代理环境变量，配合 -I 参数（只获取响应头，不下载网页内容），响应非常迅速：

curl -I https://www.google.com
  • 判断标准：在国内网络下，只要能正常拿到 HTTP/1.1 200 OK（并且看到响应头里带类似 Proxy-Connection: keep-alive 或目标服务的特征头），就完全足以证明当前终端走代理的链路已经通了，日常验证到这一步就足够了。

4. 补充：如何查看出网 IP 及归属地？

虽然用 curl -I 已经能够确认代理可用，但如果想“眼见为实”，看一眼当前终端到底是从哪个海外节点的 IP 出去的，还可以进一步通过命令行查询出网 IP 与归属地。

  1. 海外接口查出网 IP：

    curl https://ifconfig.me #或 curl https://checkip.amazonaws.com
# 返回示例：
66.90.xxx.xxx

  2. 国内接口查 IP 归属地：

    curl cip.cc/66.90.xxx.xxx
# 返回示例：
IP      : 66.90.xxx.xxx
地址    : 美国
运营商  : FDC芝加哥机房
数据二  : 美国 | FDC芝加哥机房
数据三  : Singapore Singapore Singapore | FDCservers.net  
URL     : http://www.cip.cc/66.90.xxx.xxx

说明:

在代理软件默认的**规则分流模式（Rule 模式）**下，直接用国内网站（如 curl cip.cc）查是没有用的，因为国内域名会自动触发直连放行。
所以这里的方法是：用海外接口查出网 IP，再用国内接口反查归属地。

小贴士：

  • 关于 Git 定向代理：如果开启代理主要为了加速 GitHub，也可以不配全局环境变量，直接给 Git 配置针对域名的定向代理，省心且不影响国内代码平台(不过我一般不配置~)： 
    git config --global http.https://github.com.proxy http://127.0.0.1:7890
git config --global https.https://github.com.proxy http://127.0.0.1:7890
  • 关于 PowerShell 里的 curl：在现代 PowerShell（如 PS 7+）中敲 curl 就是真实的 curl 命令；如果在老旧的 Windows PowerShell 5.1 环境中遇到 curl 被解析成 Invoke-WebRequest 别名导致报错，显式敲 curl.exe 即可。
